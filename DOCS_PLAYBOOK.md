### URL de una página

`baseUrl` es `/docs/` y `routeBasePath` es `/` (ver `docusaurus.config.ts`). Los prefijos numéricos de carpeta y archivo **se eliminan** de la URL:

| Archivo | URL |
|---|---|
| `docs/02-core-features/01-projects.md` | `/docs/core-features/projects` |
| `docs/01-getting-started/04-dashboard.md` | `/docs/getting-started/dashboard` |

### Estructura de carpetas


El orden del sidebar lo da el prefijo numérico del archivo (`01-`, `02-`…) y `_category_.json`. Una página nueva solo necesita su `.md` en la carpeta correcta.

### Convenciones de nombres

- **Páginas:** `NN-slug-en-ingles.md`, con `NN` consecutivo dentro de la carpeta. Front-matter obligatorio:


- Toda imagen lleva **texto alternativo** descriptivo y un **pie de foto** en cursiva en la línea siguiente.

## 2. Estándar de redacción y estructura pedagógica

### Tono

Español, claro, directo y orientado al usuario final (investigadores, IPs, Reviewers y Managers). Habla de lo que el usuario ve y hace («Pulsa **Nuevo Proyecto**»), no de la implementación. Los nombres de botones, campos y menús van en **negrita y tal como aparecen en la UI en español**.

### Fuente de verdad: el código, no el encargo

**Documenta lo que hace el código, no lo que dice el prompt o la memoria.** Antes de escribir reglas de negocio, léelas en el frontend (`group/src/…`) y, si hay permisos, en el backend (`core/config/packages/security.yaml` y voters). Ejemplo real de esta sesión: el encargo decía que solo *Aprobado* exigía fechas; el código (`ProjectForm.tsx`) las exige también en *Denegado* y pide además el *ID Económico*. Si el código contradice el encargo, **documenta el código y avisa al responsable**.

Etiquetas reales de la UI: `group/src/locales/es.json`. Rutas: `group/src/routes/Router.tsx` y `adminRoutes.tsx`.

### Estructura de cada página de módulo

1. **Propósito general** y vista de pájaro / listado histórico (con captura del listado).
2. **Búsqueda y filtros** (con captura del panel de filtros abierto).
3. **Permisos requeridos** según el rol (`User`, `Contributor`, `Reviewer`, `Manager`), en un bloque `:::info[Permisos requeridos]`.
4. **Flujo paso a paso** de creación/edición, con el **comportamiento dinámico** del formulario (campos condicionales, reglas de negocio). Las reglas críticas van en `:::warning[…]` y, si dependen de un estado, en una **tabla comparativa** estado × campo.
5. Cierre con un `:::tip[…]` de uso práctico (opcional).

### Roles

La jerarquía real es lineal: `ADMIN → MANAGER → REVIEWER → CONTRIBUTOR → USER`. Solo se documentan los 4 roles operativos; `ADMIN` únicamente como nota técnica. Verifica el permiso exacto de cada acción antes de afirmarlo (hay discrepancias conocidas, ver §3 de `PLAN_DOCUMENTATION_PLAYWRIGHT.md`).

## 3. Reglas estrictas de sintaxis Docusaurus v3 / MDX

> **Incidente real (2026-10-01):** la página de Proyectos se publicó con `:::warning Título` y se veía el `:::` como texto plano. `npm run build` **no falló**: Docusaurus trata una admonición no reconocida como texto, no como error. Solo se detecta mirando el DOM renderizado (§5).

Tipos válidos: `note`, `tip`, `info`, `warning`, `danger` (y `caution`).

Reglas obligatorias:

1. **Título entre corchetes pegados al tipo:** `:::warning[Título aquí]`. La sintaxis de Docusaurus 2 (`:::warning Título`) **no funciona** en v3.
2. **Línea en blanco inmediatamente después** de la apertura `:::tipo[…]`.
3. **Línea en blanco inmediatamente antes** del cierre `:::`. Nunca pegar `:::` a una línea de lista (`-`, `*`, `1.`): se convierte en parte de ese elemento y el bloque no se cierra.
4. El cierre `:::` va **solo en su línea y sin indentación**.
5. Línea en blanco antes de la apertura y después del cierre.

### Incorrecto

````md
:::warning Campos obligatorios al aprobar un proyecto
Al cambiar el estado a **Aprobado** se exige:
- **Fecha de Inicio** y **Fecha de Fin**.
- **ID Económico**.
:::
````

Fallos: título sin corchetes; texto pegado a la apertura; `:::` pegado al último elemento de la lista.

### Correcto

````md
:::warning[Campos obligatorios al aprobar un proyecto]

Al cambiar el estado a **Aprobado** se exige:

- **Fecha de Inicio** y **Fecha de Fin**.
- **ID Económico**.

:::
````

Sin título también es válido (`:::tip`), pero sigue necesitando las líneas en blanco si el contenido incluye listas.

### Otras reglas MDX

- `<`, `{` y `}` en texto plano rompen MDX: escapa (`\<`, `\{`) o ponlos entre backticks.
- Los enlaces entre páginas usan ruta relativa al archivo con extensión (`./01-projects.md`) para que el build detecte enlaces rotos.
- Tablas Markdown: línea en blanco antes y después.

## 4. Automatización de capturas con Playwright

### Ubicación y comando

- Script: `docs/screenshots/docs-screenshots.spec.ts` (config: `docs/screenshots/playwright.config.ts`).
- Ejecutar **desde `docs/`**, con frontend (`:5173`) y API (`:8080`) levantados y los fixtures de demo cargados:

  ```bash
  cd docs && npm run screenshots
  ```

  (`npm run screenshots` = `playwright test -c screenshots/playwright.config.ts`).
- Playwright es dependencia de desarrollo de `docs/`. Si faltan los navegadores: `npx playwright install chromium`.
- Variables opcionales: `APP_URL`, `GROUP_SLUG`, `DOCS_USER`, `DOCS_PASSWORD`.
- Salida: `docs/static/img/docs/<carpeta>/NN-….png`. `test-results/` está en `.gitignore`.

### Sesión y credenciales

- Login real por la UI en un `beforeEach` (`/auth/login`, campos `#email` y `#userpwd`, botón `button[type=submit]`) y espera a `/<groupSlug>`.
- Usuario por defecto: **`reviewer@sciencemanager.demo`** / `Demo1234!`. Un Reviewer ve **Nuevo Proyecto** y los formularios de edición; para pantallas solo de Manager (usuarios, catálogos, `publications/new-manual`…) usa `manager@sciencemanager.demo` vía `DOCS_USER`.
- Para documentar permisos de otros roles: `researcher0@sciencemanager.demo` (Contributor) y `user@sciencemanager.demo` (User). Todas las cuentas de demo usan `Demo1234!`.
- **Nunca** uses `AntonioM.Rodriguez@uclm.es` (cuenta real) en capturas. Credenciales completas: `memories/CREDENCIALES_ACCESO.md`.
- Antes de cada test se fija `localStorage`: `msoc-language = es` y `theme = light`.

### Viewport, modo y esperas

- `viewport 1440×900`, `deviceScaleFactor: 2`, `colorScheme: 'light'`, `locale: 'es-ES'` (`test.use` al inicio del spec).
- **Esperas obligatorias antes de `screenshot()`** (helper `settle(page)`): `networkidle` **y** que no queden skeletons (`.animate-pulse`) en el DOM. Para tablas, además `expect(locator('table tbody tr').first()).toBeVisible()`.
- Tras una animación (cambio de selector, desplegable), `waitForTimeout(300–800)` y **mover el ratón fuera** (`page.mouse.move(700, 700)`); si no, la captura sale a mitad de transición (pasó con el selector 3M/6M/12M).

### Páginas largas: no usar `fullPage`

`fullPage: true` pega la barra lateral y la cabecera **fijas** a mitad de imagen. Usa el helper `shot(page, path)`: amplía el viewport a `document.documentElement.scrollHeight`, sube al inicio y captura sin `fullPage`. Para recortes (p. ej. solo la parte superior) usa `clip`.

### Estados dinámicos

Siempre se captura el **estado**, no solo la pantalla:

| Qué | Cómo (selectores reales) |
|---|---|
| Panel de filtros abierto | `page.locator('button:has(svg.lucide-sliders-horizontal)').click()` |
| Cambiar un selector de estado | `page.locator('#status').selectOption('approved')` y esperar a que aparezca el campo condicionado (`#finalAmount`) |
| Selector temporal del panel | `page.getByRole('radio', { name: '6M' }).click()` y `settle` (el grupo es `page.getByRole('radiogroup')`) |
| Campos del formulario | Por `id`: `#title`, `#projectCode`, `#acronym`, `#status`, `#startDate`, `#endDate`, `#finalAmount`, `#economicId` |

Prefiere `getByRole`/`id` a clases CSS. Para localizar selectores nuevos, lee el componente en `group/src/` o usa Chrome DevTools MCP.

### Resaltar el elemento protagonista

Helper `highlight(locator)`: aplica `outline: 3px solid #10b981` (+ `outlineOffset: 3px`) con `locator.evaluate(...)` **justo antes** de la captura. Úsalo solo para lo que explica el texto (selector temporal, campos obligatorios al aprobar).

### Añadir un módulo nuevo

1. Añade un `test(...)` al spec con login heredado del `beforeEach`; define `NN-` consecutivo y carpeta de destino.
2. Navega, `settle`, prepara el estado, `highlight` si procede, `shot`.
3. Ejecuta `npm run screenshots` y **abre cada PNG** para verificarlo (§5).

## 5. Checklist de verificación (antes de dar por terminada una página)

- [ ] **Imágenes:** existen en `static/img/docs/<carpeta>/`, **las he abierto** y tienen datos (sin pantalla en blanco, skeletons, spinners, transiciones a medias ni sidebar duplicado).
- [ ] **Datos sensibles:** no aparecen DNI, contratos reales ni la cuenta real `@uclm.es`.
- [ ] **Reglas de negocio contrastadas con el código**, no solo con el encargo (§2).
- [ ] **Sintaxis de admoniciones** conforme a §3 (corchetes, líneas en blanco, cierre en su línea).
- [ ] **DOM renderizado, no solo el build:**

  ```bash
  cd docs && node screenshots/verify-docs.mjs core-features/projects getting-started/dashboard
  ```

  Sale con código 1 si hay `:::` en texto plano en `article` o imágenes rotas, e imprime el nº de admoniciones (`.theme-admonition`) e imágenes de cada página. Comprueba que el nº de admoniciones coincide con los bloques `:::` del `.md`. Requiere el dev server en `http://localhost:8081/docs/` (`DOCS_URL` para cambiarlo).
- [ ] **Build sin errores ni enlaces rotos**, ejecutado **dentro del contenedor**:

  ```bash
  docker exec sci-manager-docs npm run build
  ```

  Español e inglés deben terminar con `[SUCCESS] Generated static files`.
- [ ] El servidor de desarrollo sigue sano tras el build: `docker logs --tail 5 sci-manager-docs` → `compiled successfully`.

### Trampas conocidas

| Trampa | Síntoma | Solución |
|---|---|---|
| `npm run build` **en el host** | El dev server del contenedor falla con `Module not found: /Users/…/.docusaurus` (el bind mount comparte `.docusaurus/` con rutas absolutas de macOS) | Construir dentro del contenedor. Si ya pasó: `rm -rf .docusaurus build && docker restart sci-manager-docs` |
| Build verde con admoniciones mal escritas | `:::` visible en la página | `verify-docs.mjs` (§5) |
| Vista previa Markdown del IDE | Las admoniciones siempre salen como texto plano | No es un error; comprobar siempre en `http://localhost:8081/docs/` |
| `fullPage: true` | Sidebar y cabecera repetidos a mitad de imagen | Helper `shot()` (§4) |
| Panel de **Anuncios** vacío en demo | Captura con «No hay anuncios activos» | Los fixtures no crean anuncios; añadir uno o documentarlo como estado vacío |
| Cambios sin ver en `:8081` tras editar `.md` | El watcher usa polling (≈300 ms) | Esperar unos segundos; recarga forzada (Ctrl+Shift+R) |
